# Бриф: жанрово-совпадающие профили (note-only эталон) для атрибуции

## Зачем

Атрибутируем-то **заметку**, а эталон каждого автора (`style_profiles`,
`lexis_profiles`) строится из его **комментариев И заметок с равным весом**. У
большинства авторов текст профиля на 68–87 % состоит из комментариев (у p852:
RunetX 87 %, Рантье 68 %). Комментарий — другой жанр: короткая реплика, часто в
один смайл, иная манера. Значит запрос-заметку мы сравниваем с эталоном,
собранным в чужом регистре — **это системная ошибка сопоставления, а не шум**.

Это «болезнь (б)» из разбора жанрового перекоса (идея пользователя). «Болезнь
(а)» — засорённый пул кандидатов — уже вылечена **фильтром кандидатов**
(`candidateFilter`: рецент + `-min-author-notes`), который убирает из выдачи
мёртвых и чистых комментаторов: медиана ранга настоящего автора на одиночной
невиданной заметке **135 → 11 (рецент) → 4 (рецент+жанр)**. Но фильтр правит
только КОГО сравниваем; ЧЕМ сравниваем (эталон в чужом жанре) — не трогает.
Этот бриф — про эталон.

## Идея

Строить **отдельные профили из текста ТОЛЬКО заметок** и при атрибуции заметки
сравнивать с ними. Тогда и запрос, и эталон — один жанр (register-matched).

Ключевое свойство, которое всё упрощает: note-only профиль есть **только у тех,
кто писал заметки**. То есть множество note-профилей ≈ множество правдоподобных
кандидатов жанрового фильтра. **Эталонный пул и фильтр кандидатов совпадают** —
никакой мёртвый комментатор в note-режиме физически не появится, и `-min-author-notes`
для note-режима становится встроенным по построению.

## Что уже есть (переиспользовать)

- `accumulateStyle` (`stylometry.go:85`) и `accumulateLexis` (`lexis.go:138`)
  берут текст из ДВУХ источников: `comments` и `notes` (см. срез `sources`).
  **Весь механизм note-only = собрать только из второго источника.**
- `BuildStyleProfiles` (`stylometry.go:47`), `BuildLexisProfiles` (`lexis.go:52`):
  порог `minChars`/`minTokens`, кодирование вектора, запись в таблицу, `*_meta`
  под глобальные веса. Скопировать путь.
- `loadStyleProfiles`/`loadLexisProfiles`, аттрибуторы `styleAttributor`/
  `lexisAttributor` (`attribute_batch.go`) — грузят слой и обслуживают серию
  запросов. Нужна их параметризация источником профилей.
- Комбинирование и Z: `combineScores`, `Attribution`, `rankAttribution`
  (`attribute.go`). Формула не меняется — меняется, из какого слоя пришли профили.
- Фильтр кандидатов `candidateFilter` (`candidates.go`) — в note-режиме
  рецент-срез ещё полезен (заметка могла быть написана давно неактивным note-writer
  редко, но бывает), жанр-срез избыточен (все note-профили и так пишут заметки).

## Дизайн

### Вариант A (рекомендуется): параметр genre у построения и загрузки

Не плодить таблицы, а добавить в существующие `style_profiles`/`lexis_profiles`
колонку `genre TEXT NOT NULL DEFAULT 'all'` в первичный ключ:

```sql
-- миграция v15 (или следующая свободная)
ALTER TABLE style_profiles ADD COLUMN genre TEXT NOT NULL DEFAULT 'all';
ALTER TABLE lexis_profiles ADD COLUMN genre TEXT NOT NULL DEFAULT 'all';
-- PK был (user_id) → станет (user_id, genre); в SQLite менять PK = пересоздать
-- таблицу. Проще: новые таблицы style_profiles_notes / lexis_profiles_notes
-- (см. вариант B), если ALTER PK окажется муторным.
```

Значения `genre`: `all` (как сейчас, комментарии+заметки — не ломаем текущее
поведение) и `notes` (только заметки). `*_meta` тоже завести по genre (пер-жанровые
IDF/веса — важно: IDF по заметкам иной, чем по всему корпусу).

- `accumulateStyle(ctx, dims, genre)` / `accumulateLexis(...)`: при `genre=="notes"`
  оставить в `sources` только запрос по `notes`.
- `BuildStyleProfiles(ctx, minChars, dims, genre, now)` — пишет строки с этим
  `genre`. CLI: `personas stylometry build -genre notes` / `lexis build -genre notes`.
- `loadStyleProfiles(ctx, genre)` / `loadLexisProfiles(ctx, genre)` — грузят слой
  нужного жанра.

### Вариант B (если ALTER PK муторно): отдельные таблицы

`style_profiles_notes`, `lexis_profiles_notes`, `lexis_meta_notes` — точные копии
схемы. Меньше риска для существующих данных, чуть больше дублирования кода
загрузки. **Выбрать B, если правка первичного ключа тянет пересоздание таблиц с
переносом данных** (в SQLite это именно так). Прагматично — B проще и безопаснее.

### Интеграция в скоринг

Добавить в пути атрибуции выбор жанра эталона:

- `AttributeText(..., genre string)` — грузит профили этого жанра. Дефолт для
  заметочных сценариев — `notes`; для произвольного текста оставить выбор за
  флагом.
- Аналогично `VerifyText`, `CalibrateNotes`, `AttributeIdentityNotes`,
  `loadAttributors(ctx, genre)`.
- Флаг `-genre all|notes` (дефолт `notes` для attribute/verify/calibrate — мы
  почти всегда атрибутируем заметку; но дать `all` для обратной совместимости и
  для атрибуции комментариев).
- Комбинировать с фильтром кандидатов как есть: в note-режиме `candidateFilter`
  по рецент остаётся, жанр-срез можно не подавать (все note-профили — note-writers).

### Тонкость: покрытие и откат

У автора может НЕ быть note-профиля (мало текста заметок), хотя `all`-профиль
есть. Тогда в note-режиме он не кандидат вовсе. Это корректно для атрибуции
заметки (он и не заметочник), НО в режиме валидации `-note <id>` настоящий автор
может выпасть — печатать честно: «нет note-профиля (мало текста заметок)», как
уже сделано для `WantFiltered`. Возможен гибрид (backoff): если note-профиля нет
— падать на `all`-профиль с пометкой; но начать **без backoff**, чтобы честно
измерить чистый эффект жанра.

## Критерий успеха (обязательно измерить)

Тот же held-out, что и для funcwords, ДО и ПОСЛЕ:

```
personas calibrate -notes 305964,306067,306075,306085,306127,312743 \
  -author p852 -active-days 730 -min-author-notes 1 [-genre notes]
```

- Базлайн (all-эталон + рецент + жанр-фильтр): медиана ранга **4**; 312743 —
  регистро-выброс.
- Успех note-эталона: медиана 4 → ниже, и/или 312743 поднимается (заметка 312743
  — рубленый разговорный регистр; если note-эталон Рантёва тоже «заметочный», а
  не «комментаторский», сходство может вырасти). Если не двигается — зафиксировать
  честно и не подгонять.

## Порядок относительно funcwords

**Жанровый эталон и funcwords ортогональны и складываются** — делать можно в
любом порядке, но:
- Жанровый эталон **дешевле** (переиспользует весь пайплайн профилей, новая фича —
  лишь фильтр источника) и бьёт по системной ошибке сопоставления. Сделать **первым**.
- funcwords — новый сигнал против смены регистра; сделать вторым и мерить поверх
  note-эталона.
- Оба измерять одним и тем же `calibrate` held-out, чтобы эффекты были сравнимы.

## Подводные камни

- **IDF/веса пересчитать по жанру**: лексический `*_meta` для note-режима строить
  из заметок, не переиспользовать корпусный — иначе редкость слов посчитана не в
  том распределении.
- **Порог объёма выше**: заметок у автора меньше, чем комментариев; `minChars`/
  `minTokens` для note-режима, возможно, снизить, иначе профилей останется мало
  (замерить, сколько авторов получают note-профиль при разных порогах).
- **Не ломать `all`-режим**: дефолт колонки `all`, существующие профили остаются
  валидны; note-слой строится отдельной командой.
- **Фон Z считать внутри своего жанра**: mean/std косинуса — по note-профилям, а
  не по смешанному корпусу (иначе Z несопоставим).
- Диск `archive.db` на H: — построение note-слоя быстрее all (заметок много
  меньше комментариев); операция разовая, идемпотентная (перестройка с нуля).
