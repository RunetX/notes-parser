# Бриф: зеркало lovegw в мессенджер MAX

Версия: 26.07.2026. Основано на текущем состоянии `RunetX/notes-parser` (ветка по умолчанию) и документации `dev.max.ru/docs-api`.

## 1. Цель и границы

**Цель.** Публиковать заметки с love.ngs.ru в канал MAX, переиспользуя существующий парсер, хранилище и логику зеркала без изменений.

**В объёме (v1):**
- новый пакет `internal/maxx` — реализация `mirror.Sink` поверх REST API MAX;
- публикация заметки в канал (текст + аватар автора);
- лимитер частоты, обработка 429, ретрай;
- конфигурация второго приёмника и выбор приёмника при сборке.

**Вне объёма (v1), сознательно:**
- двусторонний мост (`internal/bridge`) — ответы из обсуждения на сайт;
- ЛС-бот (`internal/dmbot`), `/login`, пользовательские сессии;
- зеркалирование комментариев и уведомления подписчикам;
- одновременная работа TG и MAX на одну заметку (см. риск R1).

Обоснование: `PostNote` — единственный метод `Sink`, не требующий модели «канал ↔ группа обсуждения», которая в MAX устроена иначе, чем в Telegram, и требует отдельной разведки.

## 2. Что уже готово в коде

Архитектура к этому подготовлена. Пакет `internal/mirror` объявляет:

```go
type Sink interface {
    PostNote(ctx, n store.Note, avatar []byte) (int64, error)
    PostComment(ctx, n store.Note, c store.Comment, avatar []byte) (int64, error)
    PostNoteImage(ctx, threadRootID int64, imageURL string, image []byte) (int64, error)
    NotifySubscriber(ctx, userID int64, n store.Note, c store.Comment) error
}
```

с комментарием «Пакет не знает про Telegram: всё мессенджер-специфичное — за Sink (сегодня tgx; задел под MAX и другие)». Мессенджер-специфика вне `tgx` торчит только в `internal/bridge` и `internal/dmbot` — оба вне объёма v1.

Значит: `love`, `store` (кроме имён колонок, см. R1), `mirror` не трогаем.

## 3. Целевая реализация

### 3.1 Пакет `internal/maxx`

Структура по образцу `tgx`, но на голом `net/http` — SDK не обязателен, API плоский REST.

```
internal/maxx/
    maxx.go        Sink: клиент, PostNote, лимитер, ретрай
    compose.go     сборка HTML-текста поста
    upload.go      загрузка медиа (POST /uploads → token) + кэш URL→token
    *_test.go      юнит-тесты против httptest-сервера
```

Методы `Sink` вне объёма v1 реализуются заглушками, возвращающими явную ошибку `ErrNotSupported`, — интерфейс должен компилироваться целиком.

### 3.2 Транспорт

| Параметр | Значение |
| --- | --- |
| Базовый домен | `https://platform-api2.max.ru` (не `platform-api.max.ru`) |
| Авторизация | заголовок `Authorization: <token>`, передача в query больше не поддерживается |
| Отправка | `POST /messages` с `chat_id` |
| Загрузка медиа | `POST /uploads` → `token` |
| Лимит | 30 rps на домен |
| Сертификат | требуется доверие к сертификату Минцифры на хосте |
| Коды | 200 / 400 / 401 / 404 / 405 / 429 / 503 |

### 3.3 Тело сообщения

```json
{
  "text": "<b>Автор:</b>\nтекст заметки",
  "format": "html",
  "attachments": [
    { "type": "image", "payload": { "url": "https://..." } }
  ]
}
```

Поддерживаемые HTML-теги MAX: `<b> <i> <u> <s> <del> <ins> <em> <strong> <code> <pre> <a href> <mark> <blockquote> <h1>..<h4>`. Пересечение с текущей разметкой `ComposeNoteMessage` (`<b>`, `<a href>`) полное, поэтому композер переносится почти дословно, включая `html.EscapeString`.

Различие с Telegram, упрощающее код: в MAX текст и вложение — поля одного сообщения, а не «фото с подписью». Значит ветвление `PostNote` по `captionLimit` (1024) отпадает: аватар всегда идёт вложением, текст всегда полный. Логику «влезает / не влезает в подпись» из `tgx.PostNote` **не переносим**.

### 3.4 Медиа

Для изображений MAX принимает прямой `url` вместо загрузки байтов. Порядок:

1. пробуем `attachments[].payload.url` с URL аватара на love.ngs.ru;
2. если MAX не смог забрать (сайт отдаёт 403 внешним клиентам / требует UA) — фолбэк на `POST /uploads` с уже скачанными байтами, которые `mirror` и так передаёт в `avatar []byte`.

Кэш `mediaCache` из `tgx` (URL → file_id) переносится один-в-один как URL → token: один автор комментирует многократно, повторно грузить не нужно.

Ограничения: изображение до 50 МБ **и** не более 7680×7680. Тип вложения — `image` (`photo` не поддерживается).

### 3.5 Лимиты и ретраи

Функция `send()` из `tgx` переносится по смыслу: пер-чатовый `rate.Limiter`, один ретрай после 429. Отличие — 429 определяется по HTTP-коду ответа, а не по типизированной ошибке библиотеки. Если MAX возвращает интервал ожидания в теле или заголовке, использовать его; иначе дефолт 5 с (как сейчас). Интервал на канал: начать с текущих 3 с, при необходимости ослабить — общий потолок 30 rps далеко.

### 3.6 Конфигурация

В `internal/config` добавить секцию рядом с `mirror_bot`:

```json
"max_bot": {
  "token": "<или env LOVEGW_MAX_TOKEN>",
  "chat_id": 0
}
```

Плюс переключатель приёмника: `"sink": "telegram" | "max"`. Env-переопределение `LOVEGW_MAX_TOKEN` по образцу существующих.

`chat_id` канала в MAX нельзя узнать запросом: он приходит в объекте `Update` на события `bot_added` / `bot_started` через `POST /subscriptions` или `GET /updates`. Метод `GET /chats` не поддерживается с июня 2026. Практически: добавить бота в канал, один раз снять `chat_id` из апдейта, положить в конфиг.

### 3.7 Точка сборки

В `cmd/lovegw/main.go` сейчас `tgx.NewMirror(...)` передаётся в `mirror.New(st, client, tg, ...)` как `Sink`. Правка: по `cfg.Sink` собрать либо `tgx`, либо `maxx`, передать в тот же `mirror.New`. Ветки `bridge`/`dmbot`/`adminAlerter` при `sink == "max"` не поднимаются (v1 — только выкладка).

## 4. Риски и открытые вопросы

**R1. Схема БД именует id сообщений по Telegram и хранит одно значение.**
`store.Note.TGMessageID`, `TGThreadID`, `store.Comment.TGMessageID` — одна колонка на заметку. Пока приёмник один за запуск (переключатель `sink`), это работает: MAX-инстанс пишет свои id в те же колонки, но в **отдельную БД** (`db_path` в конфиге). Если когда-нибудь захочется зеркалить одну заметку сразу в TG и MAX, потребуется миграция схемы на «id сообщения на пару (заметка, приёмник)». В v1 сознательно не делаем; зафиксировать как известное ограничение.

**R2. Лимит длины текста сообщения в MAX не задокументирован явно.** Telegram-константы 4096/1024 к MAX неприменимы. Выяснить экспериментально при первом живом прогоне; до тех пор текст не резать (текущий принцип «контент заметки не режем» сохраняется).

**R3. Отключение превью ссылок.** Аналога `LinkPreviewOptions{IsDisabled}` в документации не видно. Если превью будет мешать вёрстке поста, искать обходной путь.

**R4. Верификация.** Бот-токен MAX выдаётся только верифицированному юрлицу РФ (Госуслуги / бизнес-ID); самозанятость не подходит. Квота — ориентировочно до 5 ботов на организацию (данные из обзорной публикации, не из офиц. документации: **перепроверить на dev.max.ru перед регистрацией**). Ссылка канала генерируется по шаблону `idИНН_biz`, то есть канал публично связывается с ИНН организации. Учесть при решении, под каким лицом заводить.

**R5. Webhook против long polling.** Для v1 (только исходящая публикация) входящие апдейты нужны ровно один раз — снять `chat_id`. Долгоживущий приём не поднимаем, поэтому требование «в проде только webhook, HTTPS с доверенным сертификатом» на v1 не давит. При будущем мосте это станет обязательным.

## 5. План работ

1. Каркас `internal/maxx`: клиент, конфиг-параметры, компиляция под `mirror.Sink` с заглушками.
2. `compose.go`: перенос `ComposeNoteMessage`, отбрасывание caption-ветки, тесты на экранирование (`<`, `>`, `&` в имени и тексте — тот самый латентный баг из Python-версии).
3. `PostNote` против `httptest`-мока: тело запроса, заголовок авторизации, разбор ответа, извлечение id сообщения.
4. Лимитер и ретрай на 429: тест с моком, отдающим 429 и затем 200.
5. `upload.go`: ветка `url`, фолбэк на `POST /uploads`, кэш токенов.
6. Конфиг + переключатель приёмника в `main.go`.
7. (Отложено до наличия токена) живой прогон в приватный тестовый канал.

Шаги 1–6 выполняются полностью офлайн: без обращений к love.ngs.ru и без реальных публикаций.

## 6. Критерий готовности v1

- `internal/maxx.Client` удовлетворяет `mirror.Sink`, проект собирается.
- `go test ./...` зелёный, включая новые тесты `maxx`.
- `PostNote` в тестах формирует корректный запрос к `POST /messages` (домен, заголовок, `format: html`, вложение), корректно разбирает ответ, переживает 429 и повторяет отправку.
- Конфиг позволяет выбрать приёмник; при `sink: "max"` мост и ЛС-бот не поднимаются.
- Живой прогон **не** входит в критерий: он блокируется внешней зависимостью (верификация юрлица), и v1 считается завершённой без него.
