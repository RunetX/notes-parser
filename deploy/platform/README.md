# Развёртывание: выкатка и обслуживание

Семь сервисов на одном хосте, все из одного образа `lovegw:latest`: демон
`lovegw` с наблюдателями `modwatch` / `guests` / `activity`, плюс площадка —
`postgres`, `platform` (веб-морда, подкоманда `lovegw web`) и `caddy` (TLS и
отдача медиа). Адрес хоста и ключ — в памяти проекта (`deploy-host-vps`), в
репозиторий они не пишутся.

Демон переехал сюда 17.08.2026, и compose стал один. Совместить их пришлось не
ради порядка: площадку наполняет fan-out ВНУТРИ демона, поэтому писать в её
Postgres должен тот же процесс, который зеркалит, — портов у базы наружу нет и
не будет. Переезд обязан быть атомарным: `getUpdates` у Telegram
single-consumer, два экземпляра на одних токенах дают 409 и дубли в канале.

Конфигов **два**, и это намеренно: `lovegw.json` (демон и наблюдатели) держит
токены ботов, ключ шифрования кук и ключи LLM/ASR, а `config.json` (веб-морда)
— только секцию площадки. Веб-морда смотрит в интернет, и общий файл отдал бы ей
всё остальное без всякой нужды.

## Выкатка

Образ на этом хосте **не собирается никогда**: `go build` просит ~1,5 ГБ RSS и
25 минут на одном ядре — это уронило бы и площадку, и зеркало. Бинарник
собирается на рабочей машине, на хосте вокруг него оборачивается тонкий образ
(`Dockerfile.prebuilt`, distroless).

```sh
# на рабочей машине, из каталога go/
GOOS=linux GOARCH=amd64 CGO_ENABLED=0 go build -trimpath -ldflags="-s -w" -o /tmp/lovegw-linux ./cmd/lovegw
gzip -9 -c /tmp/lovegw-linux | ssh <хост> "gunzip -c > /root/platform/lovegw.new \
  && chmod +x /root/platform/lovegw.new && mv /root/platform/lovegw.new /root/platform/lovegw \
  && cd /root/platform && docker build -q -f Dockerfile.prebuilt -t lovegw:latest ."
```

Сжатый бинарник — 10 МБ вместо 32, а канал до хоста ~1 МБ/с: разница между
десятью секундами и минутой. Дальше `docker compose up -d` — пересоздаются все
сервисы на новом образе.

**Бинарником выкатка не исчерпывается.** Git-клона на хосте нет, поэтому
`docker-compose.yml`, `Caddyfile` и `postgresql.conf` живут там отдельными
копиями: правка в репозитории до хоста сама не доедет. Сверять и возить — так
(сначала diff, потому что хостовая копия могла уйти вперёд):

```sh
# из каталога deploy/platform/ рабочей машины
for f in docker-compose.yml Caddyfile postgresql.conf; do
  cat "$f" | ssh <хост> "diff -u /root/platform/$f -"
done
# и, если расхождения — ровно ваши:
cat Caddyfile | ssh <хост> "cp /root/platform/Caddyfile{,.bak} && cat > /root/platform/Caddyfile"
```

**Caddyfile проверять ДО пересоздания контейнера** — сломанный конфиг уронит
прокси, а вместе с ним и площадку целиком:

```sh
docker compose exec caddy caddy validate --adapter caddyfile --config /etc/caddy/Caddyfile
```

Меняли `postgresql.conf` — помните, что `docker compose up -d` пересоздаёт
`postgres` только если менялась и его секция compose; иначе настройки
подхватываются `select pg_reload_conf()` (для параметров с контекстом sighup).

Два условия сборки незаметны, пока не сломаются, и оба проверяются на хосте, а
не в голове:

- **PEM'ы Минцифры** должны лежать в `go/internal/maxx/cacert/` ДО сборки, иначе
  TLS к MAX не встанет: российского корневого сертификата в distroless нет. Они
  гитом не отслеживаются (`.gitignore`), так что на чистой машине их надо
  положить руками — проверка: `grep -ac "BEGIN CERTIFICATE" /tmp/lovegw-linux`
  должен дать 2.
- **ffmpeg** приезжает в образ отдельным слоем (`mwader/static-ffmpeg`) — без
  него молча отваливается распознавание голосовых. Проверка: строка
  `asr/ffmpeg` в выводе `doctor`.

## Схема

Миграции накатываются **отдельной командой**, а не стартом контейнера: схему
меняет администратор в известный момент, а не любой перезапуск.

```sh
docker compose run --rm --entrypoint /lovegw platform platform -config /config.json migrate
docker compose up -d platform
docker compose run --rm --entrypoint /lovegw platform platform -config /config.json doctor
```

`web` при расхождении версий **отказывается стартовать** — это тоже намеренно:
веб-морда, молча работающая на чужой схеме, портит данные, а не падает. У
демона правило другое и осознанно: разошедшаяся схема его НЕ роняет (он зеркалит
для живых людей), приёмник площадки просто не подключается, а админу уходит
алерт. Недоступный на старте Postgres — наоборот, отказ: это чинится
рестарт-политикой, а забытая миграция нет.

## Наполнение: сверка и бэкфилл

Площадка наполняется двумя ногами: живым приёмником внутри демона (третий
`mirror.Sink`) и сверкой `lovegw.db → Postgres`. Отдельной команды под бэкфилл
нет — первый же проход сверки на пустой базе переносит всё зеркало.

```sh
docker compose run --rm --entrypoint /lovegw platform \
  platform -config /config.json reconcile -db /data/lovegw.db
```

Гонять **на хосте**, а не через ssh-туннель: это десятки тысяч транзакций, и
время решает RTT, а не работа. Прервать безопасно — приём идемпотентен по id,
следующий проход продолжит с того же места. С работающим демоном совместимо: он
крутит ту же сверку раз в пять минут, а SQLite она только читает.

Чего сверка не делает: не ходит на сайт. Байты аватаров и иллюстраций приезжают
живым потоком (их качает демон с RU-IP), историческим строкам достаётся только
ссылка — страница такую картинку просто не рисует. Забрать их можно отдельной
командой:

```sh
docker compose run --rm --entrypoint /lovegw lovegw \
  platform -config /config.json media -limit 500
```

Обычно она не нужна — хранилище наполняется само. Нужна, когда потока нет:
17.08.2026 НГС восстановился после сбоя, но комментировать так и не разрешил, а
значит новых аватаров ждать неоткуда. **Окно закрывается вместе с сайтом**: пока
hsmedia.ru отдаёт файлы, их надо забрать. Первый прогон (17.08.2026): 151 аватар
и 31 иллюстрация за 6 минут, 178 файлов и 12 МБ на диске — дедупликация даром,
имя файла есть его sha256. Битая ссылка обход не останавливает (404 у картинок,
снесённых вместе с заметкой).

## Раскатка архива

Сверка переносит зеркало — три недели. Весь корпус живёт в `archive.db`
(4,7 ГБ, 117 588 заметок и 10,8 млн комментариев с 2004 года), и переносит его
отдельная команда:

```sh
docker run -d --name archive-import --network platform_default -m 700m \
  -v /root/archive.db:/archive.db:ro -v /root/platform/config.json:/config.json:ro \
  --env-file /root/platform/secrets.env lovegw:latest \
  platform import-archive -config /config.json -archive /archive.db
```

**Архив везти на хост НАПРЯМУЮ, а не через рабочую машину.** 18.08.2026 он
приехал с Яндекс.Диска за минуту (публичная ссылка → `cloud-api.yandex.net/v1/
disk/public/resources/download` → `curl -L`), sha256 сошлась с той, что отдаёт
API. Через ssh с рабочей машины те же 4,7 ГБ по замеру 15.08 ехали бы часами.

Замер полного прогона (18.08.2026, тот же 1 vCPU): **32 мин 36 с** — копирование
29 мин 51 с (≈ 5 000 комментариев в секунду) плюс сборка четырёх индексов
2 мин 39 с (`comments_tree` 1 м 17 с, `comments_flat` 25 с, `comments_author`
38 с, `comments_reply_to` 19 с). Перенесено 117 345 заметок, 10 707 253
комментария, 2 351 иллюстрация; база выросла с 53 МБ до **5,4 ГБ** (куча
`comments` 3,1 ГБ, её индексы 2,1 ГБ, `notes` 122 МБ). Рёбра ответов: 8 190 915
из мобильного дерева, 504 по обращению, 42 по ветке, 2 515 792 корневых; из тел
снято 4 074 386 обращений «Ник, ».

**502 на `/n/<id>` во время раскатки — штатно, а не авария.** Индексы `comments`
сняты на время наполнения (10,8 млн вставок в четыре btree больше
shared_buffers стоят случайной записи на каждую строку), поэтому страница треда
идёт перебором по таблице на 3 ГБ и не укладывается в таймаут Caddy. Лента при
этом жива: её индексы не трогаются. Восстанавливает индексы сама команда, в том
числе при ошибке; если её всё же убили между «снял» и «собрал», нужный SQL она
печатает в лог.

Порция — заметки ЦЕЛИКОМ вместе с тредами в одной транзакции: тред это связная
структура, и заметка с половиной комментариев показывается неправильно вся.
Отсюда же резюмируемость — повтор видит недовезённую заметку отсутствующей и
переносит заново. Уже зеркалённые заметки (243 из 310) пропускаются целиком: у
них есть настоящее дерево от `reply-scan` и скачанные медиа, а копия архива
беднее.

Чего эта команда не отдаёт: 11 577 комментариев дампа theloser.ru 2010 — у них
нет настоящего id сайта, грабер выдал им отрицательные. Их доносит отдельная
команда, следующим разделом.

На время наполнения имеет смысл поднять `maintenance_work_mem` до 256 МБ и
`max_wal_size` до 4 ГБ (`ALTER SYSTEM SET … ; SELECT pg_reload_conf()`), а
после — **обязательно вернуть**: на 1,6 ГиБ RAM три автовакуумных воркера по
256 МБ съедят машину. Заканчивать `VACUUM (FREEZE, ANALYZE)`: статистика нужна
планировщику (на 61 тыс. комментариев планы были другие), заморозка снимает
будущий anti-wraparound на 10,8 млн свежих строк.

Проверка после раскатки — планы и время страниц:

| что | план | запрос | страница |
| --- | --- | --- | --- |
| лента, стр. 1 | `notes_feed` | 0,35 мс | 66 мс |
| лента, стр. 5883 (OFFSET 117 560) | `notes_feed` | 171 мс | 54 мс |
| тред 499 реплик | `comments_tree` | 11 мс | 124 мс |
| тред 3 888 реплик (3,1 МБ HTML) | `comments_tree` | — | 790 мс |
| линейный вид | `comments_flat` | 2,8 мс | 77 мс |

**Грабля: `archive.db` в режиме WAL нельзя открыть с read-only файла.** SQLite
заводит рядом `-shm`, и открытие падает с «attempt to write a readonly
database». Лечится `immutable=1`, но обещание «файл не меняется» команда
проверяет: непустой `-wal` рядом — отказ, потому что читать мимо незакрытой
транзакции значит тихо потерять часть данных.

## Добор восстановленного: август 2010

Эпоха, которой нет ни на сайте, ни в раскатке архива. Комментарии до конца 2013
года НГС стёр (страница треда заметки 2010 года отдаёт ноль реплик), а уцелели
они в чужой копии — дампе WordPress-зеркала theloser.ru: 11 577 комментариев за
4–9 августа 2010 года в 337 тредах. Настоящего id сайта у них нет, поэтому под
них заведена **третья полоса идентификаторов** `[2e11..3e11)` (миграция 0007);
ключ считается из ключа архива, `2e11 + |id|`.

Сначала схема, потом добор:

```sh
docker compose run --rm --entrypoint /lovegw platform \
  platform -config /config.json migrate
docker compose up -d
docker run --rm --name restored-import --network platform_default -m 400m \
  -v /root/archive.db:/archive.db:ro -v /root/platform/config.json:/config.json:ro \
  --env-file /root/platform/secrets.env lovegw:latest \
  platform import-restored -config /config.json -archive /archive.db
```

Индексы `comments` команда **не снимает** — 11 тысяч строк того не стоят, и
502 на `/n/<id>`, штатных для раскатки архива, здесь быть не должно.

Замер прогона (18.08.2026, тот же 1 vCPU): **1 мин 11 с**, из них сама запись
7 с — остальное чтение 4,7-гигабайтного архива и `ANALYZE`. Перенесено 11 551
комментарий в 336 тредов, заведена 351 анкета-тень, 6 939 обращений ушли в рёбра,
118 заметкам вернулась подпись. Один тред (151 182) пропущен — он уже был непуст.
Проверка после: страница `/n/151011` (224 реплики) отдаётся за 77 мс, из них 144
обращения дорисованы из ребра.

Правила у неё обратны раскатке архива, и это не оговорка: раскатка пропускает
заметку, уже лежащую на площадке, а добор именно в такую и дописывает тред.
Разница в том, ЧТО означает пустой тред. У зеркалённой заметки он полон и
богаче архивной копии (там reply_scan и медиа), а у заметки 2010 года он пуст и
другим не станет никогда — источника не существует. Поэтому непустой тред
по-прежнему не трогается: это признак, что заметку вело зеркало, и такие
команда называет в логе поимённо.

Идемпотентна: ключи детерминированные, повтор пропускает уже наполненные треды.
Прервать безопасно — порция это заметка целиком вместе с тредом в одной
транзакции.

Что она делает сверх переноса строк:

- **обращение эпохи** — «Для Ник (Имя) текст» — уходит в ребро `reply_to_id` и
  срезается из тела. Ник разрешается по УЧАСТНИКАМ ТРЕДА, а не по виду строки:
  в 2010-м рядом жили «Димон» и «Димон_Таибычев». Ребро находится у 60 % реплик;
  не разрешилось — обращение остаётся текстом, потому что снятое обращение без
  ребра исчезло бы совсем;
- **возвращает подпись** заметке, которую раскатка архива записала анонимной
  (автора без анкеты она приравнивает к анониму), — теперь такому автору есть
  где жить (351 анкета третьей полосы, kind = тень). К этим теням ветеранов
  можно привязывать приглашением: `platform invite -bind`. Заметок с известным
  ником, но без анкеты, в архиве 184, а команда правит 118: остальные она не
  видит вовсе, потому что идёт по тредам, а комментариев в дампе у них нет;
- ставит тредам `ingest_state.reply_scan_skip` — на сайте их нет, и очередь
  `reply-scan` иначе ушла бы на сотни заведомо пустых страниц в закрывающееся
  окно.

**Полоса — не метка происхождения, а действующее правило.** `platout` носит в
каналы мессенджеров только НАТИВНУЮ полосу; курсор у него живёт в памяти и на
старте стоит в начале нативной, поэтому без верхней границы первый же такт
после рестарта отправил бы в канал одиннадцать тысяч реплик 2010 года. Граница
стоит в SQL исходящих запросов и закрыта тестом.

## Чтение открыто, вход — по коду в анкете НГС

**Читать площадку может кто угодно** (решение владельца, 18.08.2026): лента и
обсуждения отдаются без всякого входа, а «Вход» стоит кнопкой в правом верхнем
углу шапки, как на НГС.

От поисковиков страницы закрыты: `noindex` заголовком X-Robots-Tag и мета-тегом
плюс `Disallow: /` в robots.txt. Открывать индексацию можно только вместе с
бумагой (Ш9) — зеркало чужой переписки в выдаче это распространение
персональных данных, а согласия на него нет.

**Вход** (Ш4): человек называет номер своей анкеты, получает код
`T3H-XXXX-XXXX`, вставляет его в поле «о себе» на НГС и нажимает «Проверить».
Мы читаем анкету АНОНИМНО с мобильного vhost — визит не отмечается на сайте и
человек не появляется в чужих «гостях», то есть не палится перед модерацией
тем, что переезжает. Пароль НГС не спрашивается ни на одном экране.

Проверка двусторонняя: код в «о себе» доказывает контроль над анкетой, а кука,
выданная вместе с кодом, — что проверку начал именно её владелец. Пока код
висит в анкете, его видит кто угодно, поэтому одной анкеты мало.

После проверки — два экрана согласий (обработка и распространение, по одному:
собирать их одним документом запрещает ч. 1 ст. 10.1 152-ФЗ). Отказ откатывает
вход целиком.

### Реквизиты оператора

Попадают в ТЕКСТ согласия и потому фиксируются до первой публикации:

```sh
# в secrets.env либо прямо в platform-секции config.json
LOVEGW_PLATFORM_OPERATOR='<кто обрабатывает>'
LOVEGW_PLATFORM_CONTACT='<как с ним связаться>'
```

Пустые дают безличное «Владелец площадки» — на пилоте это правда. **Смена
реквизитов после публикации — это новая редакция документа**, и `platform
migrate` на попытку подменить выпущенную откажется с прямым текстом: молча
переписанное согласие перестаёт что-либо доказывать.

### Первый вход и первый администратор

Порядок на чистой площадке:

```sh
docker compose run --rm --entrypoint /lovegw platform platform -config /config.json migrate
# → накатит схему и опубликует тексты согласий
```

Дальше владелец входит через `/login` своей анкетой НГС (id строки станет равен
номеру анкеты), и уже потом:

```sh
docker compose run --rm --entrypoint /lovegw platform platform -config /config.json role <id анкеты> admin
```

### Служебный аккаунт: код входа в личку

Код входа уходит **личным сообщением на НГС** — это основной канал, потому что
правка поля «о себе» проходит модерацию сайта и одобряется не сразу. Отправляет
служебный аккаунт из `accounts.db`; пока его нет, вход молча работает запасным
путём (код на экране → поле «о себе»), и в логе `platform` висит
`код входа в личку слать нечем`.

```sh
# логин и пароль ВТОРОЙ анкеты — со stdin, в аргументы они не попадают
docker compose run --rm -i --entrypoint /lovegw lovegw \
  account -config /config.json login -name reserve
docker compose run --rm --entrypoint /lovegw lovegw account -config /config.json list
```

Аккаунт нужен **отдельный, а не личный**. Своя анкета владельца тоже сработала
бы, и получателю такое сообщение выглядело бы понятнее, — но код входа, идущий
от живого человека, ставит под удар его собственный аккаунт: жалоба на рассылку
прилетит именно туда. Имя аккаунта можно закрепить в `platform.site_account`;
пусто — берётся первый живой из списка.

Отправку ограничивает сам челлендж: не чаще раза в три минуты и не больше трёх
раз на анкету за час жизни кода. Ограничение обязательное, а не вежливое — вход
начинает кто угодно, а сообщение приходит настоящему владельцу анкеты, то есть
без потолка служебный аккаунт превращается в рассыльщик чужими руками.

**Если НГС недоступен** (403 с этого IP, сайт закрылся, анкету снесли), вход по
анкете просто не показывается, и остаются приглашения:

```sh
docker compose run --rm --entrypoint /lovegw platform \
  platform -config /config.json invite -bind <id участника> -days 30
```

`-bind` привязывает пришедшего к уже существующей тени зеркала — и весь его
след прошлых лет становится своим, включая обращения «Ник, » в чужих ответах.
Код печатается ОДИН раз: в базе лежит только его sha256. Непривязанному
приглашению нужен администратор (колонка `issued_by` обязательна — история
выдач это часть модерации), поэтому самое первое приглашение выдавайте с
`-bind`.

## Тесты против настоящего Postgres

Половина решений пакета `platform` живёт в SQL (маскирование анонима в SELECT,
порядок по `COLLATE "C"`, частичные индексы, `ON CONFLICT`), поэтому
интеграционные тесты идут против настоящей базы. На хосте для этого заведена
отдельная база `platform_test` — тесты **сносят в ней схему целиком** перед
каждым тестом, и в них стоит предохранитель: имя базы обязано содержать «test»,
иначе прогон падает, не тронув ничего.

```sh
ssh -f -N -L 127.0.0.1:5433:<ip контейнера pg>:5432 <хост>   # ip: docker inspect platform-pg
LOVEGW_TEST_PG_DSN='postgres://platform:<пароль>@127.0.0.1:5433/platform_test?sslmode=disable' \
  go test ./internal/platform/
```

Без переменной интеграционные тесты пропускаются, так что `go test ./...` на
машине без Postgres остаётся зелёным. Прогон через туннель — около двух минут,
почти целиком это задержки сети, а не работа.

## Под нагрузкой: чем закрыт наплыв на морду

**Что именно защищается.** Не веб-морда. Хост один, ядро одно, и на нём вместе
с площадкой живёт демон: обход ленты НГС, отправка в каналы Telegram и MAX,
боты, амвон. Наружу торчит ровно одно — Caddy перед мордой, — поэтому любой
наплыв приходит туда, а расплачивается им зеркало. Мера успеха здесь такая:
**страница может отвечать «занято», канал молчать не должен.**

Этажей четыре, и каждый закрывает то, чего не видят остальные.

| Этаж | Где | Что держит |
| --- | --- | --- |
| Край | `Caddyfile` | сроки чтения/записи, заголовок 16 КБ, тело 1 МБ, перетёртый `X-Forwarded-For` |
| Приложение | `internal/web/guard.go` | частота по клиенту с ценой маршрута, 12 запросов разом, срок запроса, тело формы 64 КиБ |
| Контейнер | `docker-compose.yml` | морде 0,6 CPU и 320 МБ, `GOMEMLIMIT`, порядок OOM: первой умирает морда, последними база и демон |
| База | `platform.WebOpts`, `postgresql.conf` | морде 4 соединения из 20 и `statement_timeout 5s`, брошенный запрос снимается (`client_connection_check_interval`) |

**Почему одного этажа мало.** Потолок в приложении не считает работу, которую
его запрос задал ПОСТОРОННЕМУ процессу: тяжёлый SELECT жжёт ядро внутри
Postgres, а не внутри морды, и `cpus: 0.6` его не касается — держат его
`statement_timeout` и четыре соединения. И наоборот: рисование страницы треда
на пять тысяч реплик это память и ядро Go, до базы ему дела нет.

**Развязка демона.** Приёмник площадки (`platsink`), исходящий обход
(`platout`) и мост (`bridge`) ходят в Postgres под сроком: 5, 10 и 15 секунд.
Занятая база означает для них честный отказ, а не ожидание, — заметка остаётся
неотправленной, следующий цикл повторит, недосланное догонит сверка. Без этих
сроков наплыв на страницы останавливал бы поток в Telegram, которому база не
нужна вовсе. У сверки свой потолок на проход (20 минут): она возобновляема, и
недоделанное берёт следующий такт.

**Ручной рычаг — самый надёжный.** Морда это отдельный контейнер:

```bash
docker compose stop platform     # площадка недоступна, зеркало и боты работают
docker compose start platform
```

Терять при этом нечего: написанное на площадке уже в базе, а читателю нужна
страница, а не аптайм. Так же можно снять и `caddy` — тогда снаружи закрыт и
сам порт.

**Что смотреть, когда «что-то происходит».** Морда пишет сводку отказов раз в
минуту — строкой на запрос их писать нельзя, наплыв тогда сам становится
нагрузкой:

```bash
docker stats --no-stream
docker compose logs -n 500 platform | grep "морда отказывала"
docker compose logs -n 200 lovegw | grep -iE "не удался|не уложилась|остан"
docker compose exec postgres psql -U platform -d platform -c "select state, count(*), max(now() - query_start) as longest from pg_stat_activity where datname = 'platform' group by state"
```

Признак, ради которого всё и делалось: пока морда отказывает по потолкам, в
логе `lovegw` **нет** строк про неотправленные заметки. Если они есть — дело не
в наплыве, а в самой базе.

**Ещё один этаж, если понадобится.** Потолок соединений с одного адреса ставится
на хосте, до TLS, и приложению об этом знать не нужно:

```bash
nft add table inet filter
nft add chain inet filter input '{ type filter hook input priority 0; }'
nft add rule inet filter input tcp dport 443 ct state new meter conns '{ ip saddr limit rate 20/second burst 40 packets }' accept
```

Правило слепое (оно не отличает читателя от робота), поэтому по умолчанию его
нет: сначала потолки в приложении, они умеют считать РАБОТУ.

**Чего здесь нет намеренно.** Капчи — она платится всеми ради редкого случая.
Банов по адресу — сырых адресов площадка не хранит нигде, и заводить их ради
блок-листа значит завести персональные данные там, где их специально нет.
Внешнего щита вроде Cloudflare — он терминирует TLS, то есть читает чужую
переписку раньше нас; для площадки с согласиями по 152-ФЗ это не защита, а
новая обработка данных чужими руками.

## Грабли, оплаченные временем

**Общий якорь `x-hardening` ломает Postgres.** Он писался под distroless-бинарник,
которому не нужно ничего, и снимает все привилегии. Официальный образ Postgres
стартует от root, готовит каталоги и переключается на пользователя `postgres`:
без `cap_add: [CHOWN, DAC_OVERRIDE, FOWNER, SETUID, SETGID]` контейнер уходит в
вечный рестарт.

**В `postgres:18` сменился PGDATA** — `/var/lib/postgresql/18/docker`, а точка
монтирования образа `/var/lib/postgresql`. Привычный по прошлым версиям путь
`pgdata:/var/lib/postgresql/data` **бьёт мимо данных**: контейнер работает, но
база живёт в анонимном томе и исчезает при первом пересоздании. Проверять
фактом: `SHOW data_directory` должен указывать внутрь тома.

**`config.json` обязан принадлежать uid 65532** — distroless работает под
`nonroot` и иначе падает на `permission denied`.

**`docker exec` без `-i`** не пробрасывает stdin: `docker exec pg psql -f /dev/stdin
< file.sql` молча ничего не выполняет и возвращает успех. Результат проверять
списком таблиц, а не кодом возврата.

**Конфиг один на семь сервисов — проверять его целиком нельзя.** Секция
`platform` нужна троим (`run`, `web`, `platform *`), а `modwatch`, `guests` и
`activity` про неё ничего не знают. Общая проверка «enabled есть, а dsn пуст —
отказ» отправила бы `guests` в рестарт-петлю из-за чужой строки (так и вышло
17.08.2026 при переезде). Проверяет тот, кто открывает базу.

**Имя compose-проекта задано явно** (`name: platform`), потому что в нём зашиты
имена томов, а в томах — база и сертификаты ACME. Файл, переложенный в другой
каталог без этой строки, поднимется на ПУСТЫХ томах, и это будет выглядеть как
пропавшая база.

## Бэкапы

**Почему это не «на всякий случай».** С 18.08.2026 в базе есть строки, которых
нет БОЛЬШЕ НИГДЕ: заметки и комментарии, написанные здесь, а не принесённые
зеркалом. Зеркальные восстановимы из `lovegw.db`, архивные — из `archive.db`, а
нативные неоткуда. Там же согласия: их потеря — это потеря основания
обрабатывать данные, то есть беда не техническая.

Делает всё `backup.sh` (в репозитории `deploy/platform/backup.sh`, на хосте
`/root/platform/backup.sh`), крон в 01:30 МСК = 05:30 Нск — самый тихий час
суток на сайте. Замер первого прохода, 18.08.2026, боевой хост:

| что | размер | чем |
|---|---|---|
| Postgres 5,4 ГБ | **760 МБ** | `pg_dump -Fc --compress=zstd:3` |
| `lovegw.db` 48 МБ | 8,2 МБ | онлайновый backup API + `zstd -12` |
| `modwatch.db` 9 МБ | 1,9 МБ | то же |
| `media/` | 153 МБ | `tar` без сжатия — там уже сжатые картинки |
| **весь проход** | **928 МБ** | **173 с** |

Хранится 7 дампов Postgres, по 14 снимков каждой SQLite и 2 копии медиа — около
5,7 ГБ при 24 ГБ свободных. Три вещи в скрипте сделаны не для красоты:

- **SQLite копируется онлайновым backup API**, а не `cp`: демон пишет
  непрерывно, и обычная копия вышла бы с разорванной транзакцией. `sqlite3(1)`
  на хосте нет, но модуль `sqlite3` в `python3` — та же библиотека.
- **Дамп проверяется сразу** (заголовок `PGDMP` и разумный размер) и до этого
  момента называется `.part`. Оборванный файл не должен выглядеть готовым:
  именно его и возьмут в тот единственный раз, когда он понадобится.
- **Формат custom, а не plain SQL** — ради оглавления и выборочного
  восстановления; сжатие zstd, потому что на одном ядре zlib вдвое дороже при
  том же размере.

### Восстановление

```sh
# всё целиком в чистую базу
docker exec platform-pg sh -c 'createdb -U "$POSTGRES_USER" platform_new'
docker exec -i platform-pg sh -c   'pg_restore -U "$POSTGRES_USER" -d platform_new --no-owner --no-privileges'   < /root/backups/pg/platform-<стамп>.dump

# одна таблица (например, только нативные заметки потерялись)
docker exec -i platform-pg sh -c   'pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --data-only -t notes'   < /root/backups/pg/platform-<стамп>.dump

# SQLite: остановить демона, распаковать, вернуть владельца
docker compose stop lovegw
zstd -d /root/backups/sqlite/lovegw-<стамп>.db.zst -o /root/platform/data/lovegw.db
chown 65532:65532 /root/platform/data/lovegw.db && docker compose start lovegw
```

Учение (`rehearse.sh <дамп>`) поднимает дамп в отдельную базу `platform_restore`
и печатает наполнение обеих рядом. Гонять его на боевом хосте можно: база
отдельная, живой не касается, места под вторую копию корпуса хватает.

**Проведено 18.08.2026**, тем же вечером, что и первый бэкап: восстановление
всей базы — **423 с**, то есть семь минут, а не «часы», как боялись. Сошлось
всё: 117 656 заметок, 10 770 745 комментариев, 23 511 личностей, согласия и
живые сессии — число в число. Разошлась одна строка, `media`: 2692 против
2288 — ровно те файлы, что добрал `platform media` уже ПОСЛЕ снятия дампа.
Расхождение такого рода и есть признак исправного снимка: он показывает момент,
а не «сейчас».

### Чего здесь нет

**Копия пока одна и лежит на том же хосте.** Это закрывает порчу базы, неудачную
миграцию и «снёс не то», но не потерю машины. Offsite обязан быть в РФ
(ч. 5 ст. 18 152-ФЗ) и требует решения владельца: куда возить и кто держит ключ.
Пока его нет, ежедневный дамп — не замена второй машине, а только её отсрочка.

**Конфиги и `secrets.env` в автоматический бэкап не входят намеренно.** В них
`LOVEGW_SECRET_KEY`, которым расшифровываются куки сессий в `lovegw.db`: копия
ключа рядом с копией базы обнуляет всё шифрование — оно защищает ровно копии.
Их бэкап делается руками и увозится ТУДА, где дампов нет:

```sh
tar -C /root/platform -c lovegw.json config.json secrets.env     docker-compose.yml Caddyfile postgresql.conf   | gpg --symmetric --cipher-algo AES256 -o /root/secrets-$(date +%F).tar.gpg
```

**Сторож есть, и он снаружи демона.** Отказ прохода уходит владельцу в ЛС, а в
10:00 МСК `backup.sh check` смотрит на возраст `last-success` и жалуется, если
удачной копии больше 30 часов. Днём, а не ночью: сообщение должно попасть на
глаза, а не в список непрочитанного. Обе дороги ведут через `lovegw alert` —
подкоманду, заведённую ровно для этого: у проекта уже есть личка владельцу, не
хватало только входа в неё для скриптов хоста. Демон про бэкапы не знает и знать
не должен — каталог копий в контейнеры не смонтирован, и базе данных нечего
делать в каталоге собственных копий.

## Секреты

`secrets.env` (пароль Postgres, DSN) и `config.json` лежат только на хосте, в
репозитории их нет и быть не должно. Пароль базы наружу не публикуется: портов у
`postgres` нет вовсе, доступ только по внутренней сети compose.
